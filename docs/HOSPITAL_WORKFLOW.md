# 1.2 影像工作站介面與 RIS／PACS 工作流程

本版把操作主軸改成「檢查工作清單 → 核對個案 → 檢視影像 → 編輯報告 → 覆核簽核 → 保留更正與稽核」。採通用影像工作站配置，未仿製特定醫院廠牌；正式院內介接需再依院方資料格式、權限與驗收條件調整。

## 畫面與實際功能

| 區域 | 已實作行為 | 資料依據 |
|---|---|---|
| 檢查工作清單 | 全部／待判讀／草稿／待簽核／已簽核、關鍵字與影像類型篩選 | SQLite 檢查資料及最新報告狀態 |
| 個案資訊列 | 姓名／研究代碼、病歷代碼、出生日期、檢查單號、項目與開單來源 | 建檔欄位；內附案例皆為研究示範管理資料 |
| 左側序列 | 切片縮圖、張數與來源說明 | 本機像素；ACDC MRI 為既有研究影像，非合成 CT |
| 中央檢視器 | 拖移、縮放、反相、切片捲動、播放、相鄰切片雙欄、候選與參考框分開 | 未產生虛構歷次影像；雙欄是相鄰切片 |
| 量測 | 兩點像素距離 | 僅 px，未以未知 PixelSpacing 虛構 mm |
| 右側報告 | 適應症、技術、比較、所見、結論、限制六欄 | 由授權人員填寫；AI 候選不自動變成診斷 |
| 簽核與更正 | 簽核前再次核對，原文鎖定；補充報告需填原因與內容 | 已登入帳號、伺服器時間及不可覆寫的版本快照 |
| 代理協作 | 六工具、補件、人工交接核准與 JSON 證據 | 沿用1.0工具執行器；報告簽核與代理任務核准各自管理 |
| 匯出 | 保存版本的列印、FHIR R4 collection Bundle | Patient、ServiceRequest、DiagnosticReport；不直接寫入院內 |

## 帳號與角色

首次啟動沒有預設帳密。請建立3–40字元的管理者帳號與12–128字元密碼。密碼以Werkzeug scrypt雜湊保存；登入後輪替session與CSRF token，閒置session期限30分鐘。相同帳號一分鐘內5次失敗後暫停登入；此限制為程序記憶體狀態，程序重啟不保留。

| 角色 | 檢視影像／報告 | 建檔／執行協作 | 編輯與簽核報告／核准交接 | 建立帳號 |
|---|---|---|---|---|
| 僅檢視 viewer | 是 | 否 | 否 | 否 |
| 資料窗口 coordinator | 是 | 是 | 否 | 否 |
| 影像覆核 radiologist | 是 | 是 | 是 | 否 |
| 本機管理者 admin | 是 | 是 | 是（本機研究管理權限） | 是 |

角色是本機研究權限，不驗證醫師執照或院方身分。簽核人一律由伺服器的登入session取得，不能在瀏覽器請求中自行指定。舊版 `/research` 研究工具頁與其影像、代理API同樣受登入與角色限制，沒有保留免登入後門。應用程式內 `access_control=False` 僅供隔離的舊流程測試使用，啟動入口不提供此開關。

## 報告狀態規則

| 狀態 | 可進行的操作 | 禁止／限制 |
|---|---|---|
| 尚未建立 | 人工編輯後儲存草稿或初步報告 | 不能直接簽核空報告 |
| 草稿 draft | 編輯；儲存；送交初步報告 | 所見／結論尚未填寫時不能送交初步報告 |
| 初步 preliminary | 修改內容；再次送交；核對後簽核 | 簽核需明確勾選本次個案、影像及報告核對確認 |
| 已簽核 final | 閱讀、列印、匯出、新增補充 | 原報告欄位不得覆寫或退回草稿 |
| 已補充 amended | 閱讀全部版本、增加下一筆補充 | 保留原文與原始簽核；補充需有內容、原因、帳號與時間 |

每次異動檢查版本號，過期操作回傳409，避免兩個頁面互相覆蓋。前端有未儲存變更提示；病例切換會清除舊報告、候選、參考框、量測與影像畫面，待新影像載入後才顯示。上述簽核不是院方憑證式電子簽章。

## FHIR R4 匯出

工作站產生 `Bundle.type=collection`，方便檢查資料結構；不是會自動執行的transaction，也不會對外呼叫FHIR伺服器。

| 本機內容 | FHIR資源／欄位 |
|---|---|
| 病歷代碼、研究姓名、性別、已提供的生日 | Patient.identifier、name、gender、birthDate |
| 檢查單號、優先順序、檢查項目 | ServiceRequest.identifier、priority、code |
| 草稿／初步／簽核／補充 | DiagnosticReport.status = partial／preliminary／final／amended |
| 報告結論與全文 | conclusion（有值才輸出）、presentedForm |
| 個案與檢查的連結 | Bundle內一致的urn:uuid參照 |

本版對匯出核心結構使用FHIR 4.0.1模型驗證，紀錄見 `evidence/fhir_validation.json`。院方Implementation Guide、用語系統、患者識別規則與接收端驗收仍需另外確認。沒有原始可信StudyInstanceUID，因此不虛構ImagingStudy、SOPInstanceUID或PACS影像URL。

## 院內介接的現況與後續資料

| 系統 | 本版狀態 | 院內整合所需 |
|---|---|---|
| HIS／RIS醫囑 | 本機建檔，不向院內開單 | 院方FHIR／HL7介面、識別與檢查碼對照、測試帳號 |
| PACS | 本機PNG／JPEG／單張DICOM匯入 | DICOMweb端點與授權、QIDO查詢／WADO取像測試、真實序列與方向資訊 |
| 報告回寫 | 本機FHIR JSON匯出 | 接收端profile、憑證、簽章與院方核准的測試案例 |
| 身分 | 本機帳號與角色 | 院方SSO／AD／OIDC及部門／個案資料範圍 |
| 稽核 | 讀取檢查、報告版本、簽核、FHIR匯出與登入事件 | 院方稽核留存與外部可信保存；本機雜湊鏈無法抵抗完整資料庫重寫 |
| AI與AMD | ST-CAC介接與Lemonade客戶端 | 原始模型、完整CT序列、PN54與GPU實際驗收；未提供NPU加速 |

本地研究帳號目前可依角色檢視本機全部案例，未實作院級分科與患者資料範圍；服務仍只綁定loopback。不要將此部署直接視為已驗證的醫院正式生產系統。

## 觀看與驗證

`Hospital_Workstation_Preview.html` 可直接開啟觀看唯讀畫面；它內嵌研究MRI與樣式，不包含帳號session、可操作的後端或對外連線。這是介面預覽，不是實際瀏覽器驗收截圖。

完整系統：依README安裝與啟動、建立帳號後操作。舊的資料夾可以繼續使用，啟動時SQLite新增醫院式資料表，內附三個影像案例新增明確標記的研究管理資料；原代理工作與任務保留。

本次43項Python回歸與9項DOM／真實HTTP整合檢查通過，另有FHIR五種狀態輸出結構驗證。DOM測試使用jsdom且Canvas為替身，未完成真實瀏覽器視覺驗收、醫院互通或AMD實機驗收。

## 1.2 介面配置

頂部為緊湊操作列與檢查清單，開啟個案後固定顯示病歷號、出生日期、檢查單號與項目。中央黑底影像優先占用視窗空間；左側縮圖與右側報告各自捲動。狀態使用文字與有限色彩，不以卡片或儀表板呈現。F8可收合清單；文字欄位外可用左右鍵切片；Ctrl+S儲存尚未簽核且具編輯權限的草稿。登入、權限、簽核、補充報告與院內介接邊界不變。
